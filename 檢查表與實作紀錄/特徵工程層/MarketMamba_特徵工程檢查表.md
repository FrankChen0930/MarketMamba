# MarketMamba 特徵工程層 收尾檢查表

> 用途：特徵工程階段收尾前的品質把關，範圍限定在「資料→特徵/圖」這一層。
> 不涵蓋：訓練/實驗層本身的正確性（baseline階梯confound、實際訓練腳本的切分呼叫、evaluation端協定切換等），
> 那是下一個獨立要檢查的層級，進入實驗結果解讀階段時再另外處理。
> 適用範圍：`feature_spec.py`（67維規格）、`feature_engineer.py`、`kg_builder_v2.py`、`splitters.py` 完成後的最終確認。

---

## A. 特徵計算正確性與順序

- [ ] 所有時序型特徵（動能、波動度等）是否確認**先在各股獨立時間序列上計算完成**，才進行橫斷面標準化，沒有任何一條路徑順序顛倒
- [ ] 每個新增/修改的特徵，是否都跑過子集不變性測試（縮小宇宙、比對數值逐位元一致），而不是只在整個開發期間跑過一次
- [ ] `clean_and_scale` 的處理順序（winsorize → 中性化 → z-score）是否為目前唯一生效的路徑，沒有殘留舊版交錯順序的程式碼分支

## B. 中性化與標準化

- [ ] 中性化統計量（每產業/市值分組當日均值、標準差）是否僅用當天實際可得的股票池計算
- [ ] 中性化用的產業分類，是否已套用 `resolve_sector()` 與 `canonical_sector()`，確認同一支股票同一天不會有兩種產業標籤同時存在、且上市/上櫃的產業名稱已正規化到同一套分類
- [ ] `NEUTRALIZE_EXCLUDE` 名單（ETF/興櫃等不參與中性化的標的）是否與資料層的宇宙過濾邏輯（`filter_tradable_universe`）保持一致，沒有各自維護一份可能不同步的清單

## C. 缺失處理與可得性旗標

- [ ] 8個（或視全量結果調整後的數量）`Avail_*` 旗標，是否確認**完全不經過標準化**直接進入模型輸入
- [ ] 旗標的語意是否清楚區分「這個值是不是真的（可能經ffill帶下來但源頭存在過）」vs「今天當場有沒有新觀測」，且程式碼實作與文件描述一致
- [ ] 旗標判定為常數（如全量下 `Avail_Margin`／`Avail_Valuation`／`Avail_Financials` 仍為常數）的處理決策，是否已根據全量結果（而非小樣本）正式定案，並同步更新 `INPUT_DIM`
- [ ] 「整欄全缺」與「部分缺」這兩種不同性質的缺失，是否在特徵工程各處都維持區分處理，沒有某個新特徵又不小心用回統一的 `fillna(0)`

## D. 圖結構（GATv2）正確性

- [ ] KG v2 的節點是否確認全部為可交易真股票，沒有 ETF/權證混入
- [ ] 產業邊的建構是否為決定性（同一份輸入永遠得到同一張圖），沒有殘留未設種子的隨機抽樣
- [ ] 邊的排序鍵（權重＋`stock_id`決勝）是否在所有建圖路徑中一致套用，避免同權重下的任意排序
- [ ] 集團關聯邊（若採用）是否已與至少一個獨立公開來源（如財經資訊平台的「集團股」分類頁）做過交叉比對，而非僅憑單一來源判斷
- [ ] 相關性邊（選項C）與供應鏈邊，是否確認目前**未啟用**，且啟用前置條件（GAT消融證明圖有貢獻）尚未達成前不會被意外引入
- [ ] 圖結構是否有做過人工可讀的抽驗（如龍頭股鄰居是否合理），而非只檢查節點數/邊數等聚合統計量

## E. 特徵—Label 時間對齊與切分

- [ ] 特徵可得時間對照表（G1）是否涵蓋所有納入模型的特徵組，且與 `feature_spec.py` 保持同步，沒有新增特徵漏掉登記
- [ ] `assert_no_leakage()` 本身的邏輯是否已用已知的正確/錯誤案例各測過一次（避免斷言本身寫錯卻沒被發現，如本輪日曆陣列那次）
- [ ] purge/embargo 的參數（horizon、embargo_days）選擇依據是否已明確寫入協定文件，且標註「這是選擇不是定理」，避免日後被誤認為固定不變的標準值
- [ ] 訓練起點（如2013）與 CV 切分範圍是否已同步調整一致，沒有訓練起點改了、但切分器裡的日期範圍還沒跟著更新

## F. 版本管理與回歸驗證

- [ ] 協定版本切換（`MM_PROTOCOL`／`fundamentals_v2`／維度patch）是否都遵循「patch必須早於任何模型相關import」的順序保護，且該保護本身有被驗證過會正確觸發
- [ ] v1（已發表結果／現行production）的快取與程式碼路徑，是否確認完全未被本輪異動影響（逐位元比對通過）
- [ ] 本輪新增的所有腳本／規格文件（`feature_spec.py`、`docs/feature-protocol-v2.md`等）是否已標註「已凍結」或明確的版本狀態，避免之後有人誤改

## G. 進入訓練/實驗層前的交接確認（銜接下一層，不屬於本層檢查範圍但需明確交接）

- [ ] 實際訓練腳本是否已改為呼叫新的 `splitters.py`，而非舊的、已知有洩漏的 `walk_forward.py`
- [ ] 死旗標最終取捨（A1）是否已根據全量結果定案，且已反映到訓練腳本讀取的 `INPUT_DIM`
- [ ] 集團表縮減版本（A2）是否已定案並記錄採用理由
- [ ] 「B階段：一次一變因量IC delta」的六組對照（R0-R5）是否已按計畫執行，且只有量出正貢獻的改動才會被帶進後續的完整重訓

---

## 使用建議
A-F 六類是特徵工程層本身的收尾檢查，建議在正式進入訓練/實驗前逐項核對一次。
G 類是交接清單，用來確認「特徵工程做完」跟「訓練設置正確」之間沒有斷層——
這兩件事是本檢查表刻意分開處理的，因為過去幾輪的經驗顯示，每一層都有自己獨立的失敗模式，
一層驗證通過不能保證下一層自動正確。
