## 一、兩個核心決策的落地

討論稿的重點是兩個待決策事項。動手前我先對真實資料做了量測，結果改變了兩個決策的形狀。

### 決策1｜特徵可得期間異質性 → 起點 2013 + 可得性旗標

**量測發現：缺失有兩種性質完全不同的形狀，而現行程式都用同一招 `fillna(0)`。**

各資料源對 `prices_raw` 宇宙的 (日期, 股票) 命中率（%）：

| 來源 | 2005 | 2011 | 2012 | 2013 | 2016 | 2019 | 2026 |
|---|---|---|---|---|---|---|---|
| institutional（Group B 骨幹 20 維）| 9.6 | 16.6 | **56.3** | **73.9** | 79.4 | 78.6 | 93.3 |
| margin | 58.0 | 87.3 | 88.3 | 91.2 | 92.3 | 92.0 | 89.8 |
| daytrade | 0 | 0 | 0 | 0 | 76.0 | 81.1 | 78.0 |
| per | 20.7 | 96.8 | 96.3 | 96.7 | 96.9 | 96.0 | 72.9 |
| securities | 0.3 | 4.1 | 4.5 | 5.4 | 9.9 | 8.2 | 48.8 |
| foreign_shareholding | 0 | 0 | 0 | 0 | 0 | 94.0 | 92.2 |
| holdings | 0 | 0 | 0 | 0 | 0 | 97 | 100 |

- **整欄全缺**（daytrade 2014 前、holdings/foreign_shareholding 2018 前）
  → 當日全市場同值 → 橫斷面 z-score 自動歸零 → **本身無害**，
  但模型無從知道「這一維今天是關著的」。
- **部分缺**（institutional 2005–2011 僅 10–18%）
  → 被補的 0 與「淨買超恰為 0」這種**合法的 0** 無法區分
  → 模型改為學習「這支有沒有被資料涵蓋」這個**選擇性代理變數**。

第二種才是要處理的，也是原討論稿沒有區分的。

**落地**：
- 訓練起點 2012 → **2013**（institutional 覆蓋率跨過 74% 的台階）
- 新增 **8 個 `Avail_*` 旗標**（Group B 6 個、Group C 2 個），INPUT_DIM 59 → **67**
- 旗標語意 = 「這個值是不是真的」（可能經 ffill 帶下來，但源頭存在過），
  **不是**「今天當場有沒有新觀測」——後者反映的是公布頻率而非資料有無
- 旗標**完全不做標準化**：0/1 若逐日 z-score，「全市場都有」與「全市場都沒有」
  兩個相反狀態都會變成 0，等於自我抵銷

### 決策2｜GATv2 圖結構 → 先重建乾淨的產業圖 + GAT 開關消融

**量測發現：現行的圖不是「可以更好」，是壞的。**

| 項目 | 舊圖 | v2 |
|---|---|---|
| 節點 | 42,864（**只有 2,510 是真股票**，其餘 ETF/權證）| 2,245（全為可交易真股票）|
| 邊 | 642,451 | 32,083 |
| 滾動相關性邊 | **0 條**（動態層從未生效，例外被 try/except 吞掉）| 不含（見下）|
| 供應鏈邊 | 358 條，來自 **regex 抓 HTML 裡所有 4 位數字** | 移除 |
| 產業邊連法 | **未設 seed 的 `random.sample`**，每次重建都不同 | 決定性 |
| 2330 的鄰居 | 電器電纜、化學工業、綠能環保 | 聯電、聯發科、日月光、環球晶、創意 |

2330 的產業邊之所以一條都沒有，是因為每節點上限 15 條依權重排序，
4 條集團邊（0.8）+ 11 條爬蟲垃圾（0.6）把名額佔滿，同業邊（0.5）全被擠掉。

**v2 的產業邊**：每支股票連到同產業中市值最大的 5 支（產業龍頭）+ 市值排序最鄰近的 10 支
（規模相近者最具可比性）。排序鍵含 `stock_id` 決勝 → 同一份輸入永遠得到同一張圖。

**v2 刻意不含**：相關性邊（那是選項 C，且現行寫法有 look-ahead——
用整份資料最後 60 天算好套用到 2005 年的樣本）；產業鏈邊（留給 Phase 4-A 用正式對應表）。

## 二、過程中額外挖出的四個問題

這些都不在原本的計畫裡，是執行時被量測逼出來的。

### 1. 外資持股資料有系統性缺口（旗標第一次跑就抓到）

`Avail_ForeignShare` 精確卡在 50% 讓我去追，結果不是程式錯，而是真的缺資料。
**199 支 2018 年前就上市的公司沒有歷史外資持股資料**，只有 2026-05-06 起直連回補的 58 筆。

拆開來看是兩件不同的事：

| 類別 | 支數 | 受影響列數（2018-01~2026-04）| 性質 |
|---|---|---|---|
| **仍在交易** | **43** | **85,938（2.29%）** | 真的資料缺口，可修 |
| 已下市 | 156 | 6,810（0.18%）| 存活者偏差，交易所不公布已下市股，修不了 |

43 支仍在交易的**全部是 9 開頭**，而且是一整段連續區間：
9802、9902、9904–9912、9914、9917–9919、9921、9924–9934…
（寶成、豐泰、巨大、中鼎、美利達、櫻花、新保、中視…）全是活躍的上市公司。

**確認是單一來源的孤立問題**，不是 FinMind 的通病——七個逐日來源的
「首碼 1–8 vs 首碼 9」覆蓋率對照：

| 來源 | 首碼 1–8 | 首碼 9 | 差距 |
|---|---|---|---|
| institutional | 82.1% | 86.8% | −4.7 |
| margin | 82.3% | 97.9% | −15.6 |
| daytrade | 76.7% | 87.7% | −11.0 |
| per | 94.8% | 91.5% | +3.3 |
| market_value | 94.6% | 99.9% | −5.2 |
| securities | 11.5% | 13.8% | −2.4 |
| **foreign_shareholding** | **95.1%** | **8.5%** | **+86.6** ← 只有這個異常 |

**修復可行性已實測**：TWSE `MI_QFIIS` 端點有完整歷史，
2018-01-15 / 2020-06-15 / 2023-03-15 / 2026-04-15 四個日期都回 925–1,083 支，
且 9904 / 9910 / 9921 / 9933 **每一天都在**。
資料在交易所那邊一直都有，是 FinMind 沒抓到。
`fetch_foreign_shareholding_twse_direct()` 已存在且吃 date 參數，
回補約 2,050 個交易日 ≈ 1 小時（見第五節 D 的建議）。

### 2. `stock_info` 同一快照日期同時給大類與細類 → 2330 被標成「電子工業」

實測 **605 組 (股票, 日期)** 有兩種以上產業標籤：

```
106  電子工業 ↔ 電子零組件業      56  化學生技醫療 ↔ 生技醫療業
102  電子工業 ↔ 半導體業          30  化學生技醫療 ↔ 化學工業
 79  電子工業 ↔ 光電業
 71  電子工業 ↔ 電腦及週邊設備業
```

`load_stock_info(latest_only=True)` 的 `drop_duplicates(keep="last")` 在日期相同時
是**依 parquet 列序任意挑一個**，於是台積電落在「電子工業」這個 250 支的早年大類。

**解法**：新增 `feature_spec.resolve_sector()`，優先序 = 現行細類 > 早年大類
（電子工業／化學生技醫療）> 板別標籤（創新板股票／存託憑證）。

### 3. 產業分類名稱跨市場不一致

TPEX（上櫃）與 TWSE（上市）對同一個產業用不同名稱：

```
居家生活(11) vs 居家生活類(22)      其他電子類(53, tpex) = 其他電子業(27, twse)
數位雲端(12) vs 數位雲端類(24)      金融業(10, tpex)     = 金融保險(46, twse)
綠能環保(24) vs 綠能環保類(17)      觀光事業(殘留 1 支)   = 觀光餐旅
運動休閒(18) vs 運動休閒類(10)      創新版股票            = 創新板股票（錯字）
```

不正規化的話，同一個產業會沿「上市/上櫃」被切成兩個互不相連的群——
而那條界線在經濟上毫無意義。**解法**：`feature_spec.canonical_sector()`。

順帶量了 PIT 限制：2023→2026 標籤變動的 207 組裡，
前十大轉換幾乎全是交易所分類改版（觀光事業→觀光餐旅 41、其他→居家生活/運動休閒/綠能環保、
電子商務業→數位雲端類、創新「版」→創新「板」），**真正的公司重新分類只有個位數**
→ 用最新分類回推歷史做中性化可接受，但這是量測結果不是假設。

| 錯誤 | 實際 |
|---|---|
| 鴻海集團含 2353 宏碁、6005 群益證 | 兩者皆為獨立公司 |
| 國泰集團含 2884 玉山金、9910 豐泰 | 獨立金控／製鞋業 |
| 富邦集團含 2883 開發金、5880 合庫金 | 皆為獨立金控 |
| 遠東集團含 2401 凌陽科技 | 與遠東系無關（遠東新世紀是 1402）|
| 友達集團含 3481 群創 | 是競爭對手 |
| 「台積電生態圈」「聯發科生態圈」 | 不是集團，用 0.8 表達「從屬」語意上就錯 |

### 三個實作上的關鍵決定

1. **`feature_spec.py` 放 production 套件而非 `experimental/`**
   `feature_engineer.py`（production）需要旗標定義才能產生旗標欄，
   而 production 不可以 import experimental（依賴方向會反向）。

2. **維度切換一律 runtime patch，不改 `config.py`**
   本機那份刻意保持 56 維、不進 git。沿用 `baseline_common` 既有慣例。

3. **協定版本用環境變數 `MM_PROTOCOL` 而非 argparse**
   67 維的 config patch 必須發生在 import 期、早於任何 `from marketmamba...`，
   而 argparse 那時還沒執行。

### 一個必踩的坑（已加保護）

`architecture.py` 是 `from config import GROUP_DIMS, INPUT_DIM`——**import 當下就綁值**。
事後才 patch，`FactorGroupedEmbedding` 會**靜靜地**沿用 59 維切片，不報錯、無徵兆，
直到 IC 莫名其妙很差為止。`patch_config_67d(strict=True)` 會直接擋下這個順序錯誤，
且擋下時 config 不會被半途改壞（已實測）。

### 子集不變性測試（`V6/scripts/test_feature_invariance.py`）

宇宙 30 支 → 5 支，驗「時序特徵有沒有偷吃到橫斷面資訊」。
與上面的回歸測試驗的**不是同一件事**：回歸驗「改動沒影響舊行為」，
子集不變性驗「換一批股票進來、同一支股票的歷史特徵不能變」。
`baseline_common` 的 rolling 特徵（2026-07-27 修正的 G4）就是踩了後者。

| 關卡 | 預期 | 實測（40 支 → 8 支，2018 起）|
|---|---|---|
| [1] `build_features(v2=False)` | 逐位元相同 | **`0.000e+00`**，59 欄 × 16,346 列無差異 ✓ |
| [2] `build_features(v2=True)` | 只有 PER/PBR 因當日橫斷面校準而變 | 差異欄位 = `['PER','PBR']`，且路徑確實被執行 ✓ |
| [3] `clean_and_scale` 值 | 應該要變（證明橫斷面有生效）| 最大差 **2.139** ✓ |
| [3] `clean_and_scale` 排序 | 扣掉合法機制後排序不變 | **2,079 天 Spearman 1.000000** ✓ |
| [4] Group D macro | 與宇宙無關 | **`0.000e+00`** ✓ |

#### 這支測試寫了四版，每一版都被自己打臉（值得記下來）

**第一版：[2] 綠燈但空轉。** 樣本挑的全是老牌大型股，官方 PER 覆蓋率極高。
`_derive_valuation_fallback` 的最後一行是
`official.where(obs).combine_first(calc).combine_first(official)`——
只要那一列有官方觀測，官方值直接勝出，自算與校準完全不參與。
**跟樣本大小無關，是選樣的問題**（我一開始誤診為「≥100 筆重疊樣本的門檻沒過」）。
修法：照 `test_valuation_v2.py` 的作法，刻意挑一半「缺官方 PER」的股票；
並把警告改成**硬性斷言**——沒踩到路徑就不該給綠燈。

**第二～四版：[3] 的斷言錯了三次。** 我原本以為「z-score 單調 → 排序必然不變」，
但實際有**三個合法會改變排名的機制**，逐一追出來才對：

| 機制 | 說明 | 排除的觀測 |
|---|---|---|
| (a) winsorize 同分 | 夾到同一個 1%/99% 邊界的股票變同分；兩個宇宙的分位數不同 | 275 |
| (b) **NaN 填補** | 尾端 `fillna(0.0)` = 「該宇宙的橫斷面平均」。實例：2018-08-13 的 1240 標準化前是 NaN，填成 0 之後在 full 宇宙排第 1（其他 7 支 z-score 全正）、在 subset 排第 6（其他值含負數）。兩邊都是正確陳述 | 40 |
| (c) 橫斷面統計量 | **這才是要驗的對象**——(a)(b) 扣乾淨後必須完全一致 | — |

(b) 是最初兩版都沒想到的。這也是為什麼「一個什麼都沒測到的測試不該是綠燈」
必須寫成斷言而不是警告——警告會被讀過去，斷言不會。

**1b 值得特別說**：`clean_and_scale` 的迴圈從「逐欄 winsorize+z-score 交錯」重構成
「全部 winsorize → 中性化 → 全部 z-score」三段。數學上等價，
但**等價不等於逐位元相同**，實測了才敢說 V6.1 零影響。

### 切分洩漏的具體量化

現行 `walk_forward.py` 是 expanding window、train/test 直接相鄰、零 purge。
實測對照：訓練集結束於 **2023-12-29** 時，其 60 日 label 一路延伸到 **2024-04-08**
——測試期前三個月在訓練時就被看過。

purge/embargo 參數：`horizon` = label 最長天數（多 horizon 取 max = 60）、
`embargo_days` = **20 交易日**（最長 rolling 窗是 60 天，20 天是嚴謹度與樣本量的折衷；
**這是選擇不是定理**，已寫進協定）。

| 初版 | （沒想過會變）| 失敗 |
| 二版 | winsorize 同分 | 排除同分後**仍失敗**，同一天同一個數值 |
| 三版 | 逐日看資料才發現 | **NaN 填補**：`fillna(0.0)` = 「該宇宙的橫斷面平均」。2018-08-13 的 1240 標準化前是 NaN，填成 0 後在 full 排第 1（其他 7 支 z-score 全正）、在 subset 排第 6（其他值含負數）。兩邊都是正確陳述 |

→ 扣掉 (a) winsorize 同分 275 筆與 (b) NaN 填補 40 筆之後，
   2,079 天 Spearman **1.000000**，那才是真正在驗 z-score 的單調性。

**18. 回補耗時預估樂觀一倍**
只算了 `SLEEP_SEC`（1.2s），沒算網路往返。實測每天 2.6s，
40 分鐘的預估實際是 71.8 分鐘。→ 預估要用實測速率，不是理論下限。

## 七、方法論教訓（延續資料層那份）

1. **聚合數字會蓋掉問題，按類別拆解才看得到真相。**
   產業標籤變動率「39.6%」看似嚴重，拆開才發現幾乎全是交易所分類改版；
   外資持股缺失率整體只有 2.5% 的列，按代號首碼拆開才看到 9xxx 是 82.8%。

2. **旗標的價值在它上線第一天就兌現了。**
   `Avail_ForeignShare` 卡在 50% 這個「太乾淨不像真的」的數字，
   直接把一個藏了 8 年的資料缺口挖出來。
   決策1 的論證原本是理論性的，現在有實證。

3. **等價不等於逐位元相同。**
   `clean_and_scale` 的三段重構在數學上顯然等價，但仍然實測比對了才敢說零影響。

4. **斷言抓到的第一個錯，是斷言自己寫錯的。**
   `assert_no_leakage` 初版拿 `train ∪ test` 當日曆，被 purge 掉的那段不在陣列裡，
   `+horizon` 個位置跨過缺口，把正確的切分誤報成洩漏。
   方向雖然反了，但這正好說明「日曆」這種看似顯然的東西有多容易寫錯。

5. **手寫的關係表會無聲地腐爛。**
   集團表裡「鴻海集團 → 群益證」這種錯誤存在多久沒人知道，
   因為圖從來沒有被人眼看過一次。**收尾一定要印出人類看得懂的抽驗**，
   不能只印節點數與邊數——舊圖的統計數字看起來一切正常。
