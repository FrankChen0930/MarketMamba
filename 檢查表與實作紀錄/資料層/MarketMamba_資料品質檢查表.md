# MarketMamba 資料品質與資料處理檢查表

> 用途：獨立於現有已發現問題之外的交叉驗證基準。
> 適用範圍：~2,900 檔 TWSE 橫斷面資料、多來源備援管線（Yuanta API → Yahoo Finance → FinMind）、每日推論流程。
> 使用方式：逐項檢查，每項標記「通過 / 有疑慮 / 不適用」，「有疑慮」附上具體樣本（股票代號＋日期）。

---

## A. 存活偏誤與股票池建構

- [ ] 股票池是否為 **point-in-time**（每個歷史時間點的股票池 = 該時間點實際存在、可交易的股票），而非「用今天還在市的 ~2900 檔，往回套用到歷史所有時間點」
- [ ] 下市股票（下市日、原因：合併/下市/破產）是否完整保留在歷史訓練資料中，而非被移除
- [ ] 下市股票下市前最後幾筆資料是否正常（常見問題：下市前資料異常稀疏、成交量歸零但價格未同步更新）
- [ ] 新上市股票（IPO）的**掛牌首日**與**蜜月期價格劇烈波動**是否有特殊處理或標記（新股上市初期價格行為模式與一般股票不同，可能污染橫斷面統計）
- [ ] 股票池的產業分類、代號是否有隨時間變更（改名、代號重複使用）但資料庫未同步更新的情況
- [ ] 股票池數量隨時間變動（新股/下市股）造成的不規則性，是否用固定寬度矩陣＋預設值（如 0）補滿——若補滿的部分未被明確標記為缺失值，會被模型誤當成真實資料

## B. Look-ahead 與時間點正確性（Point-in-Time Correctness）

- [ ] 財報類特徵使用的日期，是**財報實際公告日**還是**財報所屬期間結束日**（例如 Q1 財報期間結束 3/31，但實際公告可能在 5 月中，用 3/31 當作特徵可得日會造成 look-ahead）
- [ ] 財報是否有**重編（restatement）**紀錄，若有，特徵是否用了「重編後」的數值但當時市場只看得到「原始公告」數值
- [ ] 三大法人／融資融券等每日盤後公布的資料，特徵可得時間點是否正確對齊到**下一個交易時段開始前**，而非當天盤中就可用
- [ ] 指數成分股調整（如台灣50成分股變動）公告日與生效日是否有時間差，特徵建構是否用了「公告後才知道」的成分股名單去反推更早的時間點
- [ ] Label（未來報酬）的計算起點，是否確實從「特徵可得的下一個有效交易日」開始，而非特徵當天收盤
- [ ] 合併（merge）多來源資料時，用來對齊的「日期」欄位，是否已確認每個來源該欄位的實際定義一致（例如是否有來源的「日期」其實是資料寫入時間，而非資料所屬的交易日）——這是多來源合併最基礎、卻最容易被忽略的錯位來源

## C. 公司行為調整（Corporate Actions）

- [ ] 除權息是否使用**還原股價**（adjusted price）計算報酬，而非原始收盤價（未還原會在除息日產生假的價格跳空）
- [ ] 現金增資、私募、庫藏股等會影響股數/股價的事件，是否正確反映在還原價格與市值計算中
- [ ] 減資（尤其是彌補虧損式減資）是否正確處理，這類事件價格變動幅度大，容易被誤判為極端報酬
- [ ] 股票分割/合併（雖然台股較少見但仍存在，如面額變更）是否正確調整歷史價格序列
- [ ] 不同資料來源（Yuanta / Yahoo / FinMind）對同一檔股票同一事件的還原邏輯是否一致——**這是多來源備援架構特別需要注意的一項**，三個來源的還原股價計算方式可能不同，備援切換時若無縫接軌會產生價格序列斷點

## D. 台股特殊交易機制

- [ ] 漲跌停（±10%）鎖住的交易日，是否正確標記「當天可能無法實際成交」，而非直接用收盤價當作可執行價格
- [ ] 全額交割股、處置股、注意股等交易限制狀態是否有欄位標記，並在訊號生成/組合建構階段被排除或特殊處理
- [ ] 單日成交量極低（甚至零成交）的股票，特徵計算（如報酬率）是否會產生異常值或除以零的問題
- [ ] 停牌（暫停交易）期間的資料是否正確處理（不應該有該期間的價格資料，或應明確標記為缺失而非用前一日價格填補）
- [ ] 平盤以下不得放空的限制，是否已反映在策略可執行性的假設中（如果 MarketMamba Conviction 之後有做空部位）

## E. 缺失值與資料完整性

- [ ] 各特徵的缺失比例是否有系統性監控（例如某段期間某類特徵大量缺失，可能是資料源本身斷線，而非個股沒有資料）
- [ ] 缺失值填補方式（前值填補、產業中位數、直接剔除）是否因特徵類型而異，且填補邏輯不會造成 look-ahead（例如用「當天」產業中位數填補，但產業中位數本身包含了未來才會知道的同業資訊）
- [ ] 三大法人／融資融券等資料在**非交易日或特定假期**的缺失，是否與交易日曆正確對齊，而非誤植為股票本身無資料
- [ ] 多來源備援切換時（Yuanta 主源失效切到 Yahoo/FinMind），切換點前後的資料是否有重複、遺漏或數值不連續的情況

## F. 極端值與統計異常

- [ ] 中性化／標準化後的殘差，是否仍存在遠超合理範圍的極端值（可能代表原始資料本身有誤，而非真實市場行為）
- [ ] 極端報酬率（單日 ±10% 以上，若非漲跌停觸發）是否逐筆覆核，排除資料錯誤（如價格單位錯誤、除權息未還原）而非真實暴漲暴跌
- [ ] 市值、成交量等量級跨度極大的特徵，是否確認取用對數或排序轉換前的原始單位一致（例如误把「張」和「股」混用，市值差 1000 倍）

## G. 特徵與 Label 的時間對齊

- [ ] 每個特徵的「計算所需資料截止時間」與「該特徵被允許使用的最早時間點」是否有明確對應表，避免不同特徵各自對齊、但整體拼在一起時出現不一致的可得時間
- [ ] 橫斷面標準化（z-score/rank）是否**只用當天可得的股票池**去算，而非誤用了「事後才確定的完整股票池」
- [ ] Label 的預測期間（例如未來 20 日報酬）遇到**交易日曆非連續**（國定假日、颱風假）時，天數計算是否以「交易日」而非「日曆日」為準
- [ ] **特徵計算順序**：時序型特徵（如動能、波動度）是否確實**先在各股各自的時間序列上計算完成，才進行橫斷面標準化**——若順序顛倒（先對原始數值做橫斷面標準化、再拿標準化後的值去算時序特徵），該特徵會被跨股票資訊污染，且此類錯誤不會反映在維度或缺失值檢查上，通常只會表現為 IC 異常偏低但難以溯源

## H. 即時推論管線特有項目

- [ ] 每日盤後資料到位的時間點，與模型實際推論觸發的時間點之間是否有足夠緩衝（資料源可能延遲更新）
- [ ] 即時推論用的特徵計算邏輯，是否與訓練時的特徵計算邏輯**完全共用同一份程式碼**（而非分別維護兩份邏輯相近但實際有差異的程式，這是實務上最常見、也最難察覺的訓練/推論不一致來源）
- [ ] Supabase 後端寫入的推論結果，時間戳記是否為「資料實際所屬交易日」而非「程式執行的當下時間」，避免前端顯示與回測資料時間軸對不上

---

## 使用建議
逐項標記後，優先處理「C. 公司行為調整」中跨資料來源一致性、與「H. 即時推論管線」中訓練/推論邏輯共用性這兩項——實務上這兩類問題最容易被忽略，也最容易在正式上線後才被發現。
