# 台股資料源實作雷區

> 建立：2026-07-27（實作 `margin` / `daytrade` 直連 fetcher 期間累積）
> 用途：**寫新 fetcher 前先看這份**。以下每一項都是實測撞到的，共同特徵是
> **不會拋錯、不會 HTTP 4xx/5xx、`stat` 還是 `'ok'`**，只有資料是錯的。

---

## 0. 一句話總結

台股官方端點的失敗模式幾乎都是「靜默成功」。因此每個 fetcher 都必須有**三道硬性檢查**：

1. **回傳日期核對** —— `response['date']` 必須等於請求日期，不符就 `return None`
2. **有效列數核對** —— 不是 `len(rows) > N`，而是「實際解析出數值的列數」
3. **恆等式數值驗證** —— 用資料自身的會計關係驗證欄位對映，印出不成立比例

---

## 1. 端點忽略 `date` 參數，回傳當天資料

**最嚴重的一類。** 舊的 `fetch_prices_tpex_direct` 打
`openapi/v1/tpex_mainboard_daily_close_quotes`，實測傳
`2026-07-16` / `2026-07-24` / `2026/07/16` / `20260716` / **完全不傳**，
五種情況回傳**逐位元相同**的資料，首列 `Date` 永遠是當天（民國 `'1150727'`）。
而舊版又把 `"Date": date_str` 硬寫進每一列 → **抓今天的報價、蓋上你要求的日期**。

實測後果（2026-07 期間，prices_raw 的 OTC 列 vs 交易所真值）：

| 指標 | 舊 OpenAPI 來源 | 修好後 `/www/zh-tw/afterTrading/otc` |
|---|---|---|
| Volume 比值 median | 0.93（p10 0.38 / p90 2.20） | 0.986 |
| Volume 偏差 >2 倍 | 248 / 835 檔 | 1–5 檔 |
| Close 偏差 >2% | 214 / 835 檔 | **0 檔** |

**指紋**：偏差隨「請求日期距今越遠」越大（07-16 比 07-24 更糟）。看到這個模式就要懷疑端點回的是當天。

**對照組價值**：同一天 TWSE `MI_INDEX` 來源的列 Volume 比值 median 1.0011、Close 零偏差——
一邊乾淨一邊爛，就能定位問題在哪個來源，而不是在 prices_raw。

## 2. TPEX 只認 `YYYY/MM/DD`，TWSE 認 `YYYYMMDD`

`https://www.tpex.org.tw/www/zh-tw/margin/balance` 實測：

| 請求 date | 回傳 date | 筆數 |
|---|---|---|
| `2026/04/27` | `20260427` ✅ | 896 |
| `20260427` | **`20260727`**（當天） | 913 |
| `2026-04-27` | **`20260727`**（當天） | 913 |

全部 `stat='ok'`。TWSE（`MI_MARGN`、`TWTB4U`、`MI_INDEX`）則正確認 `YYYYMMDD`。
**兩邊格式不同，不要共用日期字串處理。**

## 3. 缺 `type` 參數 → `stat='ok'`、`date` 正確、但表是空的

`/www/zh-tw/afterTrading/otc` 實測：

| params | stat | date | 最大表列數 |
|---|---|---|---|
| `{date, response}` | `ok` | `20260724` | **0** |
| `{date, type:'EW', response}` | `ok` | `20260724` | 1,013 |
| `{date, type:'AL', response}` | `ok` | `20260724` | 10,128 |

`EW` = 上櫃主板；`AL` 會混入權證等。**空表不會有任何錯誤訊號。**

## 4. 「列數 > N」不能當有效性判準：非交易日會回骨架列

TWSE `TWTB4U` 對**非交易日** 2026-07-10 回 **1,209 列**，但每列只有代號/名稱、
**不足 4 個欄位**（數值欄缺失），且市場總計表為空。若用 `len(rows) > 50` 判斷有效，
就會把空殼當成有效資料寫進 parquet。

正確做法：逐列檢查 `len(row) >= 需要的欄位數` 且數值能 parse，最後看
**成功解析的筆數**是否為 0。

> 反例佐證：同一端點對週日 / 端午 / 勞動節回 **0 列**，所以它並非無腦回傳——
> 只有某些非交易日會回骨架列，更難察覺。

## 5. TWSE 與 TPEX 的欄序不同，且與直覺不同

- **融券**：TWSE `MI_MARGN` 是「買進(8), 賣出(9)」；TPEX `margin/balance` 是「券賣(11), 券買(12)」——**順序相反**
- **OHLC**：TPEX `afterTrading/otc` 是「收盤(2), 漲跌(3), 開盤(4), 最高(5), 最低(6)」——**收盤在開盤之前**

歷史教訓：TWSE `T86` 的舊 parser 在 19 欄版面下投信/自營索引錯位，抓到的是外資自營商的欄位。

**不要靠欄名猜索引，要用實測的 `fields` 陣列對映，並在 docstring 記下完整版面。**

## 6. 第三方來源本身可能有欄位錯誤（不只自己的程式會錯）

FinMind `TaiwanStockMarginPurchaseShortSale` 對**上櫃股**把
`ShortSaleSell`（券賣）與 `ShortSaleBuy`（券買回補）**標反**（上市股正確），
2010–2026 全歷史一致。

判定用的是資料自身的恆等式：

```
融券今日餘額 = 前日餘額 + 賣出 - 買進 - 現券償還
    交易所欄位  100.00% 成立
    FinMind 欄位  88.01% 成立
```

以及 `corr(ΔShort_Balance, Sale − Cover)`（正確應為正）：

| 期間 | TSE | OTC |
|---|---|---|
| 2010–2012 | +0.707（符號一致 95.2%） | **−0.845（符號一致 1.0%）** |
| 2022–2024 | +0.949（97.3%） | **−0.927（1.1%）** |

交換後 −0.927 → **+0.927**。

**教訓：交叉驗證會抓出參考來源的錯，不只抓出自己的錯。** 不要預設「跑完的 staging 檔」是對的。

## 7. 第三方來源會對非交易日產生假資料

FinMind `TaiwanStockDayTrading` 在**非交易日** 2026-07-10 有 **1,710 列**資料，
而同一天交易所、FinMind margin、prices_raw、institutional_raw 全部都沒有。

**教訓：merge 任何 staging 檔前，先用交易日曆與獨立來源核對，不能因為「跑完了」就相信。**

## 8. 不要用 `prices_raw` 當交易日曆

`prices_raw` 自己就漏了 **2026-04-27、2026-04-28** 兩個真實交易日
（交易所在那兩天有 margin 資料、非國定假日）。拿它當基準會把洞原封不動複製到
每一個下游資料源的回補範圍。

**正確做法**：掃所有平日，讓交易所 API 自己判斷哪天沒開盤（非交易日回 `None`）。
多打幾次請求的成本可忽略，而且日曆會自我修正。

> 反面案例：`2026-07-10` 經多端點交叉確認**確實不是交易日**
> （`MI_INDEX` 回「沒有符合條件的資料」、`MI_MARGN` 空、`TWTB4U` 只有骨架列）。
> 判定非交易日要用「多個獨立端點都沒有」，不能只看一個。

## 9. 混型 `Date` 欄會讓 `drop_duplicates` 靜默失效

`run_daily_update` 舊版：yfinance 路徑的 `Date` 是 `Timestamp`、TWSE/TPEX direct
是 `str`，`pd.concat` 後欄位變 `object` 混型，
`Timestamp('2026-07-22')` 與 `'2026-07-22'` 被視為不同值 →
`drop_duplicates(subset=["Date","stock_id"])` **完全失效**。

後果：2026-07-06 起每日約 1,550 列重複，818 支股票的時序特徵被污染
（2432 的 `Return_5d` 含重複 −0.53% / 去重後 +1.07%，**正負號相反**）。

**教訓：跨來源 concat 前一律先把 key 欄位正規化成同一型別。** 這條同樣適用於
寫回 parquet 時（`_append_to_parquet` 會把 Date 轉字串，與 `timestamp[ns]` 的既有檔衝突）。

## 10. 去重的 `keep` 方向是語意選擇，不是細節

多來源重複時 `keep="first"` vs `keep="last"` 決定留哪個來源的值。
本專案的價格路徑必須 `keep="first"`（yfinance 還原價優先，與歷史序列同基準）；
若留 TWSE/TPEX direct 的**未還原**價，會在同一支股票的序列裡製造還原基準接縫。

實例：`1459` 於 2026-07-22 同日兩列，Close 分別 11.85（yfinance 還原）與
9.975（交易所原始），比值 1.188。

**也要注意**：事後補救性的整檔去重若用 `keep="last"`，可能保留錯的那一列。

## 11. 「凍結比例」這類指標要排除恆為 0 的列

量測「某欄是否停止更新」時，若直接算「兩個日期的值相同的比例」，
會被大量「本來就一直是 0」的列拉高而得到假警報：

| 欄位 | 全體「凍結」 | 排除兩天皆 0 後 | 兩天皆 0 佔比 |
|---|---|---|---|
| `Short_Sale` | 59.1% | **2.5%** | 58.0% |
| `Short_Cover` | 59.7% | **4.4%** | 57.9% |

`Investment_Trust_Net` 也出現過同樣的 75% 假警報（投信對多數個股當日淨額為 0）。

## 12. 市場總計數字的分母慣例可能與個股不同

交易所公布的「當沖占市場比重」（TWSE 25.27% / TPEX 22.51%，2026-07-24）
約為 `Σ當沖股數 / Σ成交股數`（我方計算 42–49%）的**一半**，其分母採雙邊計算慣例。

**不要因為對不上總計就認定個股計算有錯。** 個股層級的有效證據是**上界**：
`當沖股數 / 成交股數` 在 TWSE max 0.9305、TPEX max 1.0000，
兩邊都沒有任何一檔 > 1 → 單位與計算方式一致。

## 13. 比率型特徵的分母要取自同一個發布者

算 `Day_Trade_Volume = 當沖股數 / 成交股數` 時，若分子取自交易所、分母取自
`prices_raw`（可能混了 yfinance 還原價/量與交易所原始量），會產生 >1 的荒謬值：
實測 5 天就有 7 列，最大 **333.33**（6708 於 2026-07-22 分母 Volume = 3 股，
交易所真值 12,050）。

而 `feature_engineer._merge_daytrade` 有 `.clip(0, 1)` —— **會把 333 靜默變成 1.0**，
製造一個看起來合理的編造值。

**兩個原則**：① 分子分母取自同一發布者、同一市場的帳 ② 比率超出理論上界時**剔除該列**，
不要 clip（缺值比編造值好）。

## 14. 同一個端點的版面會隨年份改變

TWSE `TWT49U`（除權除息計算結果表）：**2008 起 15 欄**、**2005–2007 為 17 欄**
（舊版把「權值」「息值」分成兩欄，新版合併為「權值+息值」）。

初版硬編索引，導致 2005–2007 的 **1,592 列**把「權值」當成 `value`、「息值」當成 `kind`。

最陰險的是它**只錯一半**：索引 3/4（除權息前收盤價、參考價）在兩個版面相同，
所以主要輸出 `adj_factor` 完全正確、健檢也過，只有附屬欄位錯。
若只驗證主要輸出就會漏掉。

**做法**：一律用回傳的 `fields` 陣列查欄名對映：

```python
def _col(*names) -> int:
    for nm in names:
        for i, f in enumerate(fields):
            if nm in str(f):
                return i
    return -1
```

**順帶**：`TWT49U` **支援日期區間查詢**（`startDate`/`endDate`），全歷史只要 8 次請求，
是本專案少數不必逐日迴圈的端點。抓歷史前先確認端點支不支援區間，差別是 8 次 vs 5,300 次。

## 14b. 宣告「某資料無來源」之前，要掃過參數名 × 格式的組合

TPEX `bulletin/exDailyQ`（上櫃除權息計算結果）：

```
date=2025/08/15                       → 回 20260728~20260729（前瞻窗口）✗
startDate=20250801&endDate=20250831   → 回 20260728~20260729（前瞻窗口）✗
startDate=2025/08/01&endDate=2025/08/31 → 回 20250801~20250831，150 筆   ✓
```

我因為前兩種都失敗，一度在文件與記憶裡寫下「上櫃歷史除權息無官方來源」，
並退而用 `dividend_raw` 的公式自算（誤差 median 0.024%，堪用但不精確）。
實際上官方資料一直都在，只是要**同時**用對參數名（`startDate`/`endDate` 而非 `date`）
與格式（斜線而非 compact）。

代價：上櫃還原因子覆蓋率從 **0.2% → 97.4%**，且兩市場對稱（上市 97.5%）。

**做法**：判定「無來源」前，至少交叉測試 {`date`, `startDate`/`endDate`, `d`}
× {`YYYY/MM/DD`, `YYYYMMDD`, `YYYY-MM-DD`}。這個端點的失敗模式特別陰險——
它不報錯、`stat` 正常、還回一份**格式完全正確但內容是別的東西**的資料。

## 15. 端點的歷史深度要先實測，不能假設與另一個端點相同

同一份 `prices_raw` 的兩個來源深度差兩年半：

| 端點 | 最早可用 | 實測 |
|---|---|---|
| TWSE `MI_INDEX` | 2005-01-04 | 該日 694 檔 |
| TPEX `afterTrading/otc` | **約 2007-07** | 2007-01-04 回 0、2007-07-02 回 528 檔 |

若假設兩者一樣深，2005–2007 的上櫃段會靜默變成「只有上市」的偏斜宇宙。

**做法**：抓全歷史前先用二分法測幾個日期定出真實起點，並把限制寫進腳本 docstring
與結果文件，而不是等資料出來才發現缺一塊。

## 16. 第三方欄位的「語意」要反解驗證，不能靠欄名

`dividend_raw`（FinMind）的 `CashIncreaseSubscriptionRate` 望文生義是「現金增資配股率」，
實際不是。用它套除權息參考價公式，604 筆純現金增資事件只有 **12.3%** 對得上。

**反解法**：從官方已知結果回推真實參數，再比對各候選欄位——
比值若為常數就代表對得上。

```
ref = (close + cip × r) / (1 + r)   →   r = (close − ref) / (ref − cip)
```

| 候選欄位 | 與隱含 r 的比值 median | 落在 median±1% |
|---|---|---|
| `cir` / `cir/100` / `cir/1000` | — | **12.3%** |
| `ci_shares / total_shares` | 1.0057 | **72.0%** |

線索是怎麼冒出來的：誤差最大的樣本中，2539 那筆的 `stock_ratio` 與 `cir` **數值相同**
（都是 0.27），把 `cir` 拿掉算出的參考價與官方**一模一樣** ——
兩個本應無關的欄位數值相同，是欄位語意錯配的典型指紋。

**單位也要反解**：股票股利欄位是「元/股」，換算配股率要 ÷10（面額 10 元）。
對照組「不除 10」時準確率掉到 權 1.09%、權息 0.04%，是決定性的排除證據。

## 17. 驗證結果要按類別拆解，聚合數字會蓋掉問題

同一份驗證，看法不同結論相反：

| 看法 | 結論 |
|---|---|
| 聚合：90.28% 落在 ±0.1% | 「勉強及格，可用」 |
| 拆解：息 99.69% / 權 45.95% / 權息 72.04% | 「現金部分完美，權的公式有錯」 |

聚合數字被佔 76% 的「息」事件撐高，完全蓋掉另外兩類的問題。
若只看聚合就會帶著兩個欄位錯誤直接上線。

**做法**：驗證輸出一律按「公式成分不同的類別」拆開列。
本專案的通則是**任何加權平均都可能藏著一個壞掉的子群**。

## 17b. 抓取的暫時性失敗不可以靜默變成「該區間沒資料」

建 `ex_rights_raw` 時，TPEX 的 2022–2024 區塊因**一次性網路失敗**回 `None`，
腳本照樣印「0 筆」跑完，產出一張缺了整整三年的表——而總筆數（23,700）看起來很合理。
重跑同一個請求就成功了（3,070 筆）。

發現方式是看**年度分布**：2022–2024 各約 900 筆，而 2021 是 1,485、2025 是 1,659。
凹陷的位置恰好對齊抓取區塊的邊界，那是機器造成而非市場造成的形狀。

**兩道防線**：
① 抓取失敗要重試（本專案用 3 次、遞增退避），最終仍空要**明確標記** ⚠️
② 建表結尾加「逐年 × 逐來源」的缺口檢查，任何應有資料的年份為 0 就報錯

**通則**：對外部來源的每一次請求都要假設它會偶爾失敗，
而**聚合統計看起來合理**不能當作沒失敗的證據。

## 17c. 不要在長時間全量重抓的同時，另跑打同一個主機的作業

2026-07-28：全歷史價格重抓（TWSE `MI_INDEX`，逐日 5,301 次）跑到一半時，
另外啟動了外資持股回補（TWSE `MI_QFIIS`，58 天）。
結果重抓端開始出現 `HTTP 307`——TWSE 對來源 IP 的請求頻率做了限制，
兩個作業互相排擠。

損害有限（4 天、可重跑該年度檔），但**代價不對稱**：
省下的等待時間遠小於重抓一年要花的 11 分鐘。

**做法**：
① 全量重抓期間，只做**不同主機**的作業（TAIFEX、TDCC、MOPS 各自獨立）
② 若非做不可，把 sleep 拉長並接受更慢
③ 長時作業的年度／區塊統計要印「空回應」次數，讓事後能精準定位重跑範圍

**連帶**：對正在執行中的行程修改腳本檔**不會生效**（Python 已載入舊碼）。
本次替重抓腳本加的重試邏輯只對之後的續跑有效，當下那 4 次失敗仍是裸奔。

## 17d. 「除權息」不等於「全部會改變價格基準的公司行為」

用官方除權息表做完全歷史還原後，`|單日報酬|>100%` 反而**從 184 筆上升到 273 筆**
——唯一變差的指標。追下去發現指紋：

    6240  2.35 → 40.20 (16.1×)  停牌 13 天
    2816  1.37 → 14.97 ( 9.9×)  停牌 21 天

「前收 1–3 元 → 停牌 12–23 天 → 復牌 10–40 元、倍率集中 ~10×」＝**彌補虧損減資**
（減資九成）。273 筆中 203 筆屬此類，而它們**完全不在除權息表裡**——
純減資走股票換發程序，不經過除權除息。

**官方來源**（兩者都給停牌前收盤價與復牌參考價，可直接導因子）：

| 市場 | 端點 | 註 |
|---|---|---|
| 上市 | `twse.com.tw/rwd/zh/reducation/TWTAUU` | 路徑拼字就是 `reducation` |
| 上櫃 | `tpex.org.tw/www/zh-tw/bulletin/revivt` | `startDate`/`endDate` + 斜線 |

    adj_factor = 恢復買賣參考價 / 停止買賣前收盤價格

**通則**：做價格還原時，要問的不是「除權息處理了嗎」，而是
**「還有哪些公司行為會改變價格基準」**——減資、股票分割、面額變更、
合併換股都會，而它們各有各的公告表。
**檢驗方式**：還原後若某個極端值指標不降反升，那裡就藏著一類沒處理的事件。

## 17e. TPEX 的日期格式，請求端與回應端可以不一樣

同一個 TPEX 生態系內第三次踩日期格式，但這次在**回應端**：

| 端點 | 請求端 | 回應端 |
|---|---|---|
| `margin/balance`、`exDailyQ` | 必須 `YYYY/MM/DD` | — |
| `bulletin/revivt` | 必須 `YYYY/MM/DD` | 資料列是 **7 碼緊湊民國 `1070102`** |

前兩次的教訓是「請求要用斜線」，於是回應端的 parser 也照斜線寫，結果整批解析失敗
（TWSE 同類表則是 `107年01月02日`）。

**做法**：民國日期 parser 一律同時吃三種——`107年01月02日`、`107/01/02`、`1070102`。
不要因為同一家交易所就假設格式一致。

## 17f. 換掉一份 production 資料檔時，schema 型別必須逐欄保持不變

2026-07-29 把 `prices_raw` 換成官方還原價。兩檔的 schema 差了兩處：

| 欄 | production | 新檔 |
|---|---|---|
| `Date` | `large_string`（`'2026-07-28'`） | `timestamp[ns]` |
| `src` | 無 | 有 |

**`Date` 型別若跟著換過去，會直接複製問題 9 的災難**：每日更新的 fetcher
產出的是**字串**日期，與 parquet 裡的 timestamp concat 後變成混型 `object`，
`drop_duplicates` 靜默失效 → 每天累積重複列 → 時序特徵被污染
（前一次是 10,591 列重複、2432 的 `Return_5d` 正負號相反）。

`src` 同理不進 production：每日新增的列不會有這欄，只會產生一整排 NaN。

**做法**：切換腳本先讀 production 的 schema，把新資料**對齊回去**再寫：

```python
old_cols = [f.name for f in pq.read_schema(PROD) if not f.name.startswith("__")]
out = adj.drop(columns=[c for c in adj.columns if c not in old_cols])
out["Date"] = pd.to_datetime(out["Date"]).dt.strftime("%Y-%m-%d")   # 轉回字串
out = out[old_cols]
```

寫完再讀一次 schema 比對型別，印出「與切換前一致 ✓」才算完成。
**原則：切換只該改變「值」，不該改變「型別」與「欄位集合」。**
額外的欄位／更好的型別想保留，就放在旁邊那份參考檔（本例 `prices_adj_raw.parquet`）。

## 17g. 換掉資料檔後，用它算出來的「比率型健檢指標」要重新檢查分母

切換後法人資料覆蓋率從 **96.1% 掉到 89.5%**，看起來像退步，實際是**分母變了**：
新 `prices_raw` 的宇宙從 1,948 支變 2,100 支，多出來的 133 支是 ETF，
而交易所本來就不出個股法人明細給 ETF。

套用與推論端相同的 `filter_tradable_universe` 後：**1,899 支、96.2%**，其實還微幅上升。

若不修，健檢會永遠掛一個不會消失的假警報——**而長期存在的假警報會訓練人忽略警報**，
比沒有警報更危險。

**做法**：健檢的比率指標，分母要用「下游實際使用的集合」，不是原始檔的全部。
換檔後把每個比率型指標重跑一次，任何變動都要能解釋。

## 17h. 「有 fetcher」不等於「會更新」——沒接進每日流程的源遲早停更

反覆出現的結構性成因，2026-07 至少三次：

| 源 | 症狀 | 根因 |
|---|---|---|
| `margin_raw` | 停更 3 個月 | fetcher 只寫 CACHE_DIR 單日暫存檔，**從未 append 到 parquet** |
| `per`/`securities`/`market_value` | 停更 3 個月 | **完全不在每日更新裡**，靠手動全量同步 |
| `revenue`/`financials` | 停更 118 天 | 只在 `force_rebuild=True` 時抓，平時走 `if cache.exists(): 用快取` 分支 |

三者的共同形狀是：**程式碼看起來都有在抓，但沒有任何一條路徑會在日常執行時真的寫入。**
而且都不會報錯——只會安靜地讓特徵凍結成常數。

**做法**：每個資料源都要能回答「**哪一行程式碼會在今天執行、並且真的寫入**？」
答不出來就是遲早停更。搭配健檢的停更告警（每個源設容許落後天數）當第二道防線。

## 17i. 「補最舊的 N 筆」要先排除已死的實體

月/季頻資料改成「每天補資料最舊的 N 支」的滾動更新後，實測**淨增 0 列**——
因為排序把**已下市股票**排在最前面（最舊停在 2002-02-01），
它們永遠不會有新資料，每輪都把額度耗在同一批身上，活躍股永遠輪不到。

修法是先用「`prices_raw` 最後一個交易日的宇宙」過濾（2,311 → 1,924 支），
之後單輪就從 0 列變成淨增 90 列。

**通則**：任何「挑最舊/最落後的 N 個來處理」的排程，
都要先排除**不可能再更新的實體**，否則佇列會被永久卡死的項目塞滿。

## 18. 判定可用與否要看誤差幅度，不是命中率

命中率（落在 ±0.1% 的比例）回答「有多常精準」，
但決策需要的是「不精準時錯多少」，以及**對照替代方案錯多少**。

| | median | p90 | >1% 比例 |
|---|---|---|---|
| 息 | 0.000% | 0.009% | — |
| 權 | 0.025% | 0.099% | — |
| 權息 | 0.024% | 1.019% | — |
| 合計 | — | — | 2.04% |

關鍵在於**分母要選對照組**：典型還原修正量本身是 4.5%（`adj_factor` median 0.9550），
所以這套公式平均抓到 **99.5%** 的修正量；而替代方案「不還原」會在除息日
留下完整 4.5% 的假跌幅。→ 「2% 的事件誤差 >1%」是可接受的，判定可用。

**通則**：不要拿量測結果去比對「完美」，要比對「不做這件事會怎樣」。

## 附：驗證用的恆等式清單

| 資料 | 恆等式 |
|---|---|
| 融資 | `今日餘額 = 前日餘額 + 買進 − 賣出 − 現金償還` |
| 融券 | `今日餘額 = 前日餘額 + 賣出 − 買進 − 現券償還` |
| 三大法人 | `買 − 賣 = 淨額`；`各法人淨額加總 = 合計` |
| 當沖 | `0 ≤ 當沖股數 / 成交股數 ≤ 1`（個股層級） |
| 市值 | `市值 = 收盤價 × 已發行股數`（量級抽驗） |
| 價格 | `Low ≤ min(Open, Close) ≤ max(Open, Close) ≤ High` |
| 除權息 | `參考價 = (前收 − 現金股利 + 增資認購價 × 增資配股率) ÷ (1 + 無償配股率 + 增資配股率)` |
| 還原因子 | `adj_factor = 參考價 / 前收盤價`；`> 1` 代表**減資**（合法） |
