# 資料/特徵基礎升級計畫 — 把 baseline_common 扶正成下一代基礎

> 日期：2026-07-14
> 緣起：Cowork 討論——原本考慮「開一個全新平行專案、只共用前端」重新蓋一遍 pipeline，最後決定改成**擴充 `V6/experimental/baseline_common.py` 已經驗證過的資料層**，不重寫整個系統。V6.1 全程不動，符合既有隔離原則。
> 一句話定位：方向二為了公平比較四個模型，被迫蓋出一套比 V6.1 現有管線更嚴謹的資料層（協定凍結、D0–D5 驗證方法論）。與其丟掉重寫，不如把這套已經驗證過的東西正式扶正成下一代基礎，Mamba 變成這個梯子上「多一個模型」，而不是另起一個平行宇宙。

---

## 0. 決策脈絡（為什麼不開全新專案）

你想補的「洞」，仔細看大多是**資料層**問題（存活者偏差、Close=0 損壞列、還原/未還原價接縫、point-in-time 正確性），不是模型層問題。不管包在哪個新專案裡，只要底層還是同一批 FinMind/yfinance/TWSE 資料，問題就還在。真正能解決這些洞的是「用協定驅動、逐步驗證的方法論重蓋資料層」，而這件事已經在方向二裡做出雛形了。另一方面，fetcher（含重試/欄位對映修復史）、KG 建構、訊號掃描器、LLM 報告產生器，都是踩過真實坑才長出來的資產，重寫等於冒著重新踩坑的風險換一個「看起來比較乾淨」的感覺，這個交換在你现在的時間預算下不划算。

## 1. 範圍界定

### 保留不動（沿用既有、已驗證過的工程資產，不重寫）

- 資料抓取 `fetcher.py`（FinMind + yfinance + TWSE/TPEX direct，含重試與 07-07 修復的欄位對映邏輯）
- 知識圖譜建構 `graph_builder.py`（含未來 Phase 4-A 產業鏈擴充計畫）
- 訊號掃描器 / 型態學 / 四層退場邏輯（`signals/`、`quant/pattern_scanner.py`）
- LLM 市場報告產生器 `llm/report_generator.py`
- 前端（`app/frontend`、`PersonalOS`）與現有後端 API 契約
- **V6.1（`V6/models/`、正式推論線）本身**——這是紅線，本計畫任何階段都不動它

### 升級目標：`baseline_common.py` → 正式的下一代資料/特徵基礎

現有已具備、可以直接繼承的部分：universe 過濾協定（§2）、point-in-time 驗證慣例（D5 已驗證無位移）、`clean_and_scale` 標準化、D0–D5 那套「先懷疑、再驗證」的方法論本身。

需要新增才能扶正成正式基礎的部分：

1. **序列張量輸出模式**：目前 `baseline_common` 只吐扁平 300 維（給 Ridge/GBDT/LSTM），要新增 `(N, 252, 59)` 序列輸出模式，才能餵給 Mamba+GATv2
2. **KG 邊整合點**：讓新基礎能對接 GATv2 讀取知識圖譜邊，不是只服務扁平模型
3. **修掉本次診斷發現的三個資料衛生問題**：Close=0 損壞列、還原/未還原價接縫、超限報酬複驗——直接在新基礎版本修掉，不動 V6.1 現有 pipeline
4. **協定文件正式版本化**：比照 `baseline-experiment-protocol-draft-2026-07-11.md` 的凍結模式，把新基礎的資料契約寫成可長期參照的規格文件

## 5. 隔離原則具體化：怎麼寫才不影響 V6.1（2026-07-23 新增）

原本第 1 節只寫了「V6.1 本身是紅線，不動」這個原則，但 2g（修每日更新管線缺口）這項工作**本身就必須碰 `fetcher.py` 與 `run_daily_inference.py`——這兩支正是 V6.1 每天 17:00 真的在跑的生產程式**，不像其他階段二/三項目可以整個關在 `V6/experimental/` 裡不動生產碼。這裡把「怎麼碰才安全」寫清楚，分三種情境：

**情境 A：純新增/獨立分析（階段二 2d/2e、階段三全部、方向二階梯重跑）**
- 一律新增檔案在 `V6/experimental/`，讀取現有 `Data/processed_v6/*.parquet` 或呼叫 `baseline_common.py` 既有函式，輸出寫到新的獨立檔案（例如 `V6/experimental/result/`、新的 cache 檔名）
- 不 import、不呼叫、不修改 `V6/marketmamba/models/`、`run_daily_inference.py`、`fetcher.py` 裡任何現有函式的行為
- 這類工作風險最低，可以直接動工，不需要每次都先問

**情境 B：修每日資料更新管線缺口（2g，會員碰觸生產路徑）**
- **不要**直接改寫 `fetcher.run_daily_update()` 既有邏輯（那是 V6.1 每天在用、目前跑得穩定的路徑，改壞了會直接影響真倉 dashboard）
- 做法：仿照現有「訊號掃描器」「持倉四層退場 checker」掛進 `run_daily_inference.py` 的模式（見 CLAUDE.md：`run_portfolio_check()`、`condition_analysis.json` 等步驟）——**新增一個獨立、non-fatal 的步驟**（例如 `sync_stale_fundamentals_macro()`），用 `try/except` 包住，失敗只記 log、不中斷主流程，只對那 7 個停更檔案做「當日/當週增量更新」，不做 `force_rebuild=True` 全量重抓（全量重抓 14 年資料耗時長、也沒必要——只是要接上缺的 3 個月）
- 開發時**先在 WSL 手動單獨跑**這個新步驟（不透過 Task Scheduler、不影響 17:00 排程），確認：① 抓到的資料數值合理（不是空值/亂碼）② 寫回 parquet 用 append/upsert、不覆蓋整檔 ③ 執行時間不會讓 17:00 排程總時間爆掉，穩定跑過幾天再正式掛進每日流程
- 這一步完成後，V6.1 推論吃到的 Group C（基本面）/Group D（總經）特徵會從「3 個月前的快照」變成「當日更新」——這是讓 V6.1 更健康的修復，不是拿新東西去動它，但因為改的是它每天真的在跑的檔案，必須用上面這套「先隔離驗證、再掛進生產」的方式，不能直接改完就上

**情境 C：清理既有生產資料裡的髒資料（2a Close=0 存量清理、2h 重複寫入清理）**
- 沿用專案裡已經有的既定做法（見 CLAUDE.md 決策紀錄「非交易日假資料一律整日刪除」「prices_raw 去重」等前例）：**動手刪任何一列 `prices_raw.parquet`／`institutional_raw.parquet` 既有資料前，先複製一份帶日期戳的備份**（例如 `prices_raw_backup_20260723.parquet`），且**這類刪除動作要先給你看清楚要刪的筆數/日期範圍/理由，經你明確同意才執行**——這兩個檔案是 V6.1 當下就在讀的生產資料，跟改 `V6/experimental/` 裡的東西風險等級完全不同
- 寫入端 gate（防止未來新的 Close=0 再寫入）風險較低，可以視為情境 B 的一種（新增檢查邏輯、不影響既有抓取結果），但同樣要先隔離跑過幾天確認 gate 沒有誤殺正常資料（例如興櫃股票、除息造成的合理低價）才上生產

**優先順序建議**：情境 A（階段二 2d/2e＋階段三重跑）風險最低，可以先動工；情境 B（2g 管線缺口）影響 V6.1 訊號品質，優先度其實蠻高，但需要照上面流程小心接；情境 C（既有髒資料清理）風險最高，且往往只影響歷史回測不影響當下訊號，可以放最後、有把握了再做。

| 項目 | 結果 | 證據 |

### 總結：優先處理順序

檢查表本身建議優先處理 C（跨資料源一致性）與 H（訓練/推論共用），核對結果證實兩者**確實都存在真實問題**，加上這次順便量化出的幾項，建議優先順序：

1. **C5 跨資料源還原不一致 + 2h 重複寫入**（已有 2412 具體案例，且兩者可能是同一批問題疊加）——直接影響階段二 2b 的既定工作範圍，趁修的時候一起排查

## 7. 停更資料回補執行記錄（2026-07-24～25）

> 對應 2g 的實際執行過程。這階段目標：把 2026-04-24 前後停更近 3 個月的 `per_raw`／`securities_raw`／`market_value_raw`／`margin_raw`／`daytrade_raw`／`macro_raw` 六個檔案補到最新。**本節只記錄「補資料」這件事的完整過程與結果；合併回 production 的決定與執行留到下一階段，本節寫完時五個檔案仍停在暫存區。**

### 7.4 macro_raw 修復（唯一直接動 production 的一步）

`_sync_macro_data()` 原本只抓 6 個 yfinance 系列（VIX/SPX/Gold/Oil/TNX/USD_TWD），但既有 `macro_raw.parquet` 有 12 欄，缺口是舊版（可能是更早的手動腳本）留下的欄位，現在的函式重建不出來。追查 `feature_engineer._merge_macro()` 後確認：

- `TWII_Close` 有**獨立消費者**（`signal_conditions.py` 的 regime 閘門讀它判斷 TWII 站不站上季線），不經過模型特徵管線，值得補 → **已補**，加入 `^TWII` ticker
- `US_SOX`、`CNN_FearGreed`、`TW_Biz_Signal`、`FED_Rate` 四個欄位：`_merge_macro()` 對應到的模型特徵（Fear_Greed/Business_Signal/FED_Rate，US_SOX 甚至完全沒被用到）在 V6.1 因既有的 Group D 橫斷面 z-score bug 全部歸零，且有寫死的合理預設值（50.0/23.0/4.0）兜底，不會造成任何下游錯誤 → **確認不補**，理由記錄在決策紀錄

執行方式：**先備份**（`macro_raw_backup_20260724.parquet`）→ 呼叫 `_sync_macro_data(force=True)` 全量重建（yfinance 抓 7 個系列的完整 2005-2026 歷史，約數十秒）→ 實測跑一次 `_merge_macro()` 驗證 TWII_Return/VIX/SPX/TNX 等欄位輸出的是真實數值、不是預設值。**已完成並生效於 production**。

### 7.5 意外挖出的既有 bug：`_finmind_fetch()` 參數名稱錯誤

`_finmind_fetch()` 原本送出的 HTTP 參數是 `stock_id`，但 FinMind API 實際辨識的參數名稱是 `data_id`——`stock_id` 不被辨識，等同於送出整批查詢，免費額度下一律被擋。這是**修這次資料回補之前就存在於 production 的 bug**，`fetch_prices_finmind()`（股價 yfinance 失敗時的個股備援路徑）用的也是這個函式，可能已經悄悄失效一段時間，只是這條備援路徑很少被觸發到所以沒被發現。**已修正**：改送 `data_id`。

### 7.6 事故記錄：IP 封鎖 + 背景任務不穩定 + 誤判邏輯

回補 margin/daytrade（約 2,515 檔 × 2 資料集，需要單股迴圈）過程中依序踩到三個問題，記錄下來避免以後重蹈覆轍：

1. **第一輪空轉 10.4 小時**：`_finmind_fetch_chunked` 呼叫時傳入 `stock_id=` 參數（7.5 的 bug），全部 2,515 檔 × 2 個資料集**回傳 0 筆**，但腳本當時沒有能力分辨「拿不到資料」跟「這支股票剛好沒資料」，直到跑滿全部才發現。**教訓：長時間背景任務正式啟動前，一定要先用實際呼叫路徑（不是另外寫的手動測試）跑 3-5 筆小樣本驗證，這次就是因為只驗證了手動組的 HTTP 請求、沒有验证 script 實際呼叫的函式，導致參數名稱不一致的 bug 沒被攔到**
2. **IP 被 FinMind 暫時封鎖**（`{'msg': 'ip banned', 'retry_after': 1261}`）：大量命中 400 拒絕回應被判定為異常流量，需等待約 21 分鐘解除。修正參數 bug 後先用小樣本驗證、確認未被封鎖才重新啟動
3. **背景任務本身不穩定**：修完參數 bug 後的正式回補，中途被系統中止兩次（一次跑了近 7 小時才中止、一次啟動後不到 1 分鐘就中止），原因不明（WSL 與 Windows 本身都確認正常、無重開機跡象，推測是背景執行環境的問題非腳本或資料問題）。**靠 checkpoint 機制撐過**：每處理 50 檔就寫一次進度，中斷後重跑自動從斷點接續，沒有遺失已完成的進度
4. **誤判邏輯 bug**：連續失敗提早中止的保護機制（防止重演事故 1）一開始只用「連續 N 次回傳 None」判斷，把「這批股票剛好真的沒有融資融券/當沖資料」（多為近期新股，掛牌後要等一段時間才有信用交易資格，程式碼裡常見的 `78xx` 開頭代號）誤判成封鎖而提早中止。**已修正**：中止前先送一次診斷請求，直接看 HTTP 回應內容區分「真的被擋」（400/403 + 錯誤訊息）vs「單純沒資料」（200 + success + 空陣列），只有前者才真的中止，後者重設計數器繼續跑

### 7.7 意外發現：`prices_raw` 本身也有個別交易日的缺口

回補 margin/daytrade 時，FinMind 對 **2026-04-27、2026-04-28** 兩天回傳正常資料，但這兩天在 `prices_raw.parquet` 裡完全不存在（不是週末，是平日）。加上先前已知的 **2026-07-10** 缺口（原本懷疑颱風假，這次用 daytrade 資料反證是真交易日、prices_raw 抓取失敗），目前累計**至少 3 個 `prices_raw` 個別交易日整天缺漏的實例**，時間點分散在 4 月與 7 月。已更新進第 6 節與階段二 2i，狀態從「待查」升級為「確認為真實缺口」。**這是 prices_raw 自己的問題，不是這次回補的六個檔案造成的**，但既然回補時意外驗證了另外兩個實例，一併記錄。
